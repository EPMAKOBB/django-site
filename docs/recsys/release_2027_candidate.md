## Команда переноса

`prepare_informatics_2027_release` использует slug исходного экзамена и проверяет содержимое существующих задач, а не ID из тестовой базы. Создаёт **только черновик**. Существующий чужой сезон или несовпадающую задачу не перезаписывает. Повтор своего импорта не меняет редакторские правки и не возвращает выведенные из выдачи задачи.

В каталог `FILES` положить `demo_23.txt`, `demo_24.txt`, `demo_27.txt` из проверенного комплекта 2027. SHA-256 проверяется до записи. Тексты задач входят в код (`scripts/data`), сами файлы передаются отдельно. Не подменять их одноимёнными файлами другого выпуска без повторной проверки и обновления контрольных сумм.

Пример команд **для заранее выбранного окружения**, где `DB_NAME` — настоящее имя его базы, а `FILES` и `REPORT` — подготовленные пути:

```text
python manage.py prepare_informatics_2027_release --source-exam-slug inf-ege-2026 --files FILES --report REPORT --settings=fractalschool.settings
python manage.py prepare_informatics_2027_release --source-exam-slug inf-ege-2026 --files FILES --expect-database DB_NAME --apply --report REPORT --settings=fractalschool.settings
```

Первая команда откатывает изменения базы и не пишет media. Как обычно в PostgreSQL, использованные значения последовательностей ID не возвращаются; это не создаёт записи задач. Вторая требует совпадения `--expect-database` с выбранной настройками базой. Новые вложения при ошибке импорта удаляются; существующие не заменяются. Отчёт содержит `ready_for_review` и список оставшихся замечаний. Публикация — отдельное действие в админке после проверки требований.

Ранее созданные `scripts/*sandbox*`, `complete_informatics_2027.py` и `add_informatics_2027_demo13.py` — сценарии исходного локального эксперимента. Для рабочего переноса использовать **management-команду выше**. Не восстанавливать тестовую базу поверх рабочей.

1. Состав подтверждён владельцем 20.09.2026: выпускаем только сезоны; учёт учеников и расписание — позже.
2. По решению владельца используем имеющуюся тестовую копию для репетиции, новый дамп для неё не запрашиваем. Репетиция выше проверила 0049 и импорт; полный путь 0043–0049 и backfill требует отдельной проверки на копии до сезонных миграций. Перед изменением рабочей БД на сервере сделать резервную копию для восстановления.
3. Уточнить действующий сервер, папку проекта, способ подключения и команды остановки/перезапуска Django. Старый FTP workflow относился к неудавшемуся переносу и удалён по указанию владельца; он не описывал действующий прод.
4. Разобрать известные сбои общего набора; отдельно проверить реальные формы заявок и экран учителя. Зафиксировать решение по ним перед выпуском.
5. Выполнить браузерную приёмку на копии с media: старый незавершённый вариант, история, новый ответ, запуск/завершение тренировок 2026/2027, выбор сезона существующим учеником.
6. Согласовать окно первого обновления с паузой записи ответов и фоновых задач. Выполнить резервную копию базы и media, проверить восстановление.

## Порядок выкладки после репетиции

Устаревший `.github/workflows/main.yml` удалён. Оставшийся workflow выполняет проверки, а не выкладку. До обновления main необходимо установить, нет ли внешнего автодеплоя на действующем сервере; GitHub workflow не определяет все возможные способы доставки кода.

1. Остановить запись и старые процессы, сохранить контрольные количества/примеры истории.
2. Доставить проверенный код; выполнить миграции с рабочими настройками.
3. Выполнить `audit_exam_context`, предварительный `backfill_exam_context`, затем `backfill_exam_context --apply` и повторный аудит. Сопоставить результаты с копией до обновления. [Подробный порядок и ограничения восстановления](exam_year_transition_release.md).
4. Выполнить `collectstatic --noinput` в окружении сервера. Перезапустить только новые процессы и проверить старый сезон/приём ответов.
5. Подготовить черновик 2027 management-командой; проверить отчёт, новые вложения и требования. Опубликовать через админку; 2026 оставить активным. Выбор существующих учеников не переносить принудительно.
6. Возобновить запись и фоновые задачи, повторить аудит и проверить журнал ошибок.

После начала приёма новых ответов нельзя просто вернуть старый дамп или старый код, не понимающий новые контексты. При сбое остановить новые записи, сохранить принятые данные и исправлять текущий выпуск. Конкретные команды остановки/перезапуска будут добавлены после уточнения окружения действующего сервера.
